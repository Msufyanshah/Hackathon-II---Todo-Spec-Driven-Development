# Hackathon II – Todo Spec-Driven Development Constitution

## Core Principles

### Spec-Driven Development (SDD) First
No code may be written until specifications are complete, reviewed, and approved. All implementation must be generated via AI agents (e.g., Claude Code) strictly from specs. Manual coding is prohibited; refinement happens by improving the spec.

### Engineer as Architect
The human role is system architect and spec author, not syntax writer. AI agents act as executors of validated specifications.

### AI-Native & Cloud-Native by Design
The system must evolve toward AI agents, MCP tools, Kubernetes, and event-driven architectures. Stateless services and managed infrastructure are preferred.

### Iterative Evolution
The Todo application must evolve incrementally across defined phases. Each phase builds on the previous; phases may not be skipped.

### No Manual Coding
All source code must be generated by AI agents using Spec-Kit Plus and Claude Code. If output is incorrect, refine the specification—not the code.

### Mandatory Spec Artifacts
Every feature must have: Constitution alignment, Specification (WHAT), Plan (HOW), Tasks (Atomic units). Specs must be written in Markdown and managed via Spec-Kit Plus.

### Phase-Gated Architecture Enforcement
All architectural, security, API, cloud, AI, and orchestration principles defined in this Constitution are **phase-gated**.

A principle applies **only when the corresponding phase explicitly activates it** in `/sp.specify`.

Phase I is strictly exempt from:
- API design
- Authentication / authorization
- Network communication
- Persistence
- AI agents
- Containerization
- Kubernetes
- Event-driven systems

Future phases (II–V) progressively activate these principles.

## Technology Stack and Functional Scope
Includes mandatory technology stack for each phase (Phase I: Python 3.13+, UV, etc.; Phase II: Next.js, FastAPI, etc.) and functional scope (Basic: Add/Delete/Update/View/Mark tasks; Intermediate: Priorities, Tags, Search; Advanced: Recurring tasks, Due dates).

## API & Security Principles and Quality Criteria (Phase II+ Only)
These principles apply only when a phase explicitly includes APIs, authentication, or networked services.
They do not apply to Phase I.
Includes REST API discipline, JWT-based authentication, stateless services, MCP as sole tool interface, defined tool contracts, deterministic agent behavior, container-first approach, Kubernetes-native deployment, event-driven architecture with Kafka, Dapr abstraction, correctness over creativity, spec fidelity, scalability, and demonstrability requirements.

## Phase II Activation Declaration

The following Constitution principles, previously dormant in Phase I, are now explicitly activated for Phase II.

No Phase III+ principles are activated unless stated.

### Activated Capabilities (Phase II)

#### 1. API Architecture (Activated)

The system MUST expose functionality via a RESTful HTTP API

API design MUST follow:

- Clear resource naming
- Proper HTTP verbs
- Predictable request/response schemas

APIs MUST be defined in specification documents before implementation

#### 2. Persistence & Data Modeling (Activated)

The system MUST persist data across application restarts

- A database MUST be introduced
- Data models MUST be defined in spec.md before implementation
- Migration strategy MUST be documented (even if simple)

#### 3. Multi-User Support (Activated)

The system MUST support multiple users

- Task data MUST be scoped per user
- No shared global task state is permitted

#### 4. Authentication & Authorization (Activated)

- Authentication MUST be implemented
- Authorization rules MUST be explicit in the specification
- JWT-based authentication is the default unless overridden by spec
- No hardcoded credentials are permitted

#### 5. Frontend Application (Activated)

- A web-based frontend MUST be implemented
- Frontend and backend responsibilities MUST be clearly separated
- UI behavior MUST trace back to specification requirements

#### 6. AI Code Generation Governance (Reaffirmed)

All source code MUST be generated by approved AI agents
(e.g., Claude Code, Qwen Code)

- Manual coding remains strictly prohibited
- If output is incorrect, specification refinement is the only correction mechanism

#### Explicitly Out of Scope (Still Forbidden)

The following remain inactive and MUST NOT appear in Phase II:

- AI agents or chatbots as application features
- Kubernetes or container orchestration
- Event-driven architecture (Kafka, Dapr, etc.)
- MCP tools as runtime system components
- Cloud-native scaling concerns
- Background workers or async pipelines beyond basic API needs

(These are reserved for Phases III–V.)

## Phase II Quality Gates

Phase II work MUST satisfy all of the following:

- Every API endpoint traces to a Spec requirement
- Every database entity traces to a Spec section
- Every code artifact traces to a Task ID
- No Phase III+ concepts appear in specs, plans, tasks, or code
- The system is demonstrable end-to-end (Web UI ↔ API ↔ Database)

## Governance
This Constitution is the highest authority with the hierarchy: Constitution > Specify > Plan > Tasks > Code. All code artifacts must trace back to Task IDs and spec sections. Deviations require explicit updates to this document.
